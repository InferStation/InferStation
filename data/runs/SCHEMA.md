# Run JSON Schema

InferStation stores one JSON object per measured scenario under
`data/runs/<YYYY-MM-DD>/`.

## File Names

Current serve-mode writers use:

```text
<host>-<model>-<quant>[-bsN]-<engine>-<serve-scenario>.json
```

The exact filename is generated by `scripts/bench-batch.py`. Treat the relative
path as the stable run ID; do not hand-derive it when the writer can generate it.

## Metric Semantics

- `ttft_ms`: mean client-observed time to first streamed token.
- `tpot_ms`: mean time per output token after the first token.
- `prefill_toks_per_s`: mean per-request prefill estimate. At concurrency above
  one it includes queueing effects.
- `decode_toks_per_s`: aggregate output tokens divided by wall-clock duration.
- `total_toks_per_s`: aggregate input plus output tokens divided by wall-clock
  duration.
- `pp_toks_per_s`, `tg_toks_per_s`, and `combined_toks_per_s` are compatibility
  aliases used by existing charts.
- Detailed distributions and counters live in `raw_llamabench` despite the
  historical field name.

See [`../../docs/methodology.md`](../../docs/methodology.md) for the benchmark
procedure.

## Provenance

- `image` records the requested image reference.
- `image_tag` records its tag for filtering and display.
- `image_digest` records the immutable pulled manifest digest when Docker exposes
  `RepoDigests`. New generated records should include it. Older records may omit
  it and must be interpreted together with their Actions log and release ledger.
- `log_url` and `source_url` point to the GitHub Actions run that produced the
  result.
- `engine.version` records the engine's self-reported version. It does not replace
  `image_digest`.

Validated deployment images are listed in
[`../../IMAGE_RELEASES.md`](../../IMAGE_RELEASES.md).

## Compatibility

`schema_version` remains `0` for the existing corpus. Optional fields are allowed
because older offline and early serve records remain checked in. Writers should
emit the current fields above; readers must tolerate missing optional provenance
and detailed metrics on historical records.

`usability_tag` is one of:

- `ok`: completed and suitable for normal use.
- `slow`: completed but performance is poor.
- `fragile`: completed with material operational caveats.
- `broken`: failed or unusable.
