# Serve-mode benchmark — architecture & developer guide

This is the **internal design** for the online serving benchmark: how a unit is
defined, how the dispatcher runs it, where each step lives in code, and what is
not done yet. The user-facing summary is [`methodology.md`](methodology.md); this
document is for whoever extends the benchmark.

> **Where the code lives.** The dispatcher is **not yet in this repo**. It runs on
> the 4090 dev box at `/home/amd/inferstation/admin_api/` (FastAPI + uvicorn on
> `127.0.0.1:8201`, behind nginx `/admin`). Files: `main.py` (dispatcher + serve
> flow + embedded bench client), `ingest_runs.py` (parse output → run records →
> `runs.json`), `gen_serve_units.py` (unit generator). Getting these under version
> control is a tracked gap (see below).

## Why online serving

Offline tools measure different things per engine (`llama-batched-bench` vs
`vllm bench throughput`) and don't yield real TTFT/TPOT. We instead run an
OpenAI-compatible server and a streaming client, so **both engines use one method
and one set of metric definitions**. `llama-server` and `vllm serve` have the same
interface for our purposes: `--host/--port`, `/health` (200/503), and
`/v1/completions` with `stream:true`.

## Decoupled config ↔ flow

A **unit** only *declares* what to run. One generic **flow** reads those fields and
executes every step. Every serve unit shares the same flow, so adding a model or
host is data, not code.

### Unit schema (serve mode)

A unit is a serve unit iff it carries a `serve` block. Generated by
`gen_serve_units.py`.

```jsonc
{
  "id": "bc44bb0346",                  // sha1(name)[:10]
  "name": "<model>-<quant>-<engine>@<host>/serve-stream-in512-out128-c1x4x16x32",
  "model": { "source": "/models/<file-or-dir>", "comment": "https://huggingface.co/<repo>" },
  "device": { "class": "NVIDIA DGX Spark", "host": "" },  // host empty => host_map at dispatch
  "docker": { "image": "", ... },       // image empty => _resolve_default_docker (nightly tag)
  "serve": {
    "start_cmd": "...llama-server -m /models/... --host 0.0.0.0 --port {port} -c {ctx} -np {nseq}",
    "port": 8081, "ctx": 30720, "nseq": 32,
    "health_path": "/health", "ready_timeout_s": 900, "warmup": 2
  },
  "bench": { "input_len": 512, "output_len": 128, "concurrency": [1,4,16,32],
             "endpoint": "/v1/completions", "num_prompts": null },  // null => max(c,8)
  "launch_cmd": "",                     // unused in serve mode
  "tags": { "model_series": ..., "quant": ..., "framework": "llama.cpp"|"vLLM", "custom": [scenario, engine_slug] }
}
```

`start_cmd` placeholders `{port}` `{ctx}` `{nseq}` are substituted by the flow.
`ctx` formula (llama.cpp shares `-c` across `-np` slots, each slot = ctx/nseq must
hold input+output): `ctx = ceil(nseq*(in+out)*1.5 / 2048) * 2048`. vLLM equivalent:
`--max-model-len >= in+out`, `--max-num-seqs = nseq`.

## The flow (per unit)

Built by `_build_serve_script(u)` in `main.py`; dispatched when
`_build_launch_script` sees a `serve` block (`if u.get("serve"): return
_build_serve_script(u)`). The generated host bash does:

1. **Remove stale container** — `docker rm -f <cname>`.
2. **Download model in parallel** — *(NOT IMPLEMENTED — see gaps)*. Intended to
   reuse the offline path's HF download (`_parse_model_spec` + the `hf download`
   block in `_build_launch_script`, single-file gguf with sharded fallback, or
   repo snapshot for vLLM), running alongside container start.
3. **Start container** detached: `docker run -d --net host --entrypoint /bin/bash
   <image> -lc 'export PATH=/app:$PATH; <start_cmd>'`. Image resolved by
   `_resolve_default_docker` when `docker.image` is empty.
4. **Poll `/health`** until 200 (timeout `ready_timeout_s`; exit 70 if the
   container dies, 71 if not ready in time).
5. **Warm up** — `warmup` small requests (input 64 / output 8) to absorb one-time
   costs (Vulkan shader compile: cold TTFT ~40s vs warm ~0.5s).
6. **Per-concurrency bench** — host `python3` runs the embedded client
   (`_STREAM_BENCH_CLIENT`, written to host `/tmp` via heredoc) once per level:
   `--max-concurrency $c --num-prompts <max(c,8) or override>`. Each level's
   result JSON is **streamed to stdout the moment it finishes**, wrapped in
   `>>> SERVE_RESULTS_BEGIN` / `>>> SERVE_RESULTS_END`.
7. **Stop** — `trap _serve_cleanup EXIT` removes the container and the temp client.

### Why each design choice (hard-won)

- **Fresh container per run** — no cross-run state; a crashed prior run can't
  poison the next.
- **Client on the host, not in the container** — pure stdlib (urllib + threading),
  no torch/CUDA import (which hangs in CPU-only vLLM containers). One server with
  `-np 32` serves all levels; the client caps concurrency per level.
- **Distinct prompt per request** (`random.choice(pool)`, not a fixed repeat) —
  identical prompts hit llama.cpp's prefix/checkpoint cache, which restores one
  shared checkpoint and **serializes the batch**, destroying the concurrency
  measurement (TTFT explodes, aggregate throughput drops below single-stream).
  This was a real bug. Common short words keep ~1 token/word (random letters
  BPE-explode to 3000-5000 tokens and blow the context slot).
- **Stream each level immediately** — a slow late level (e.g. conc=32 on a
  bandwidth-bound backend) timing out must not discard the completed levels. The
  ingest parser tolerates an unclosed `SERVE_RESULTS` block.
- **`num_prompts = max(c, 8)`** — a saturating wave for large c, a few samples for
  small c. The old `c*4` was untenable on memory-bound backends.

## Metrics & ingest

`ingest_runs.py`:
- `parse_unit` recognizes the serve scenario `serve-stream-in(\d+)-out(\d+)-c(.+)`.
- `_parse_serve_results` extracts per-concurrency JSON from the `SERVE_RESULTS`
  block (tolerates an unclosed block).
- `_ingest_serve` writes one run record per concurrency (`<host>-<model>-<quant>
  [-bsN]-<engine>-serve.json`), mapping serve metrics onto the dashboard axes:

| record field | serve metric |
|---|---|
| `pp_toks_per_s` / `prefill_toks_per_s` | prefill throughput = `input_len/(ttft-one_tpot_step)` per req |
| `tg_toks_per_s` / `decode_toks_per_s` | decode throughput = output tokens / wall |
| `combined_toks_per_s` / `total_toks_per_s` | total throughput = (input+output) / wall |
| `ttft_ms` | mean TTFT |
| `tpot_ms` | mean TPOT = `(latency-ttft)/(output_len-1)` |

The dispatcher auto-ingests: live per-level as each JSON streams in (a stdout line
with `mean_ttft_ms`), and a final catch-all after the process exits. Both call
`ingest_stdout` then `rebuild_manifest()` (which wipes and rewrites `runs.json` +
`raw/` from the `runs-src/` tree).

### Reading metrics correctly

Do **not** treat llama.cpp's per-slot `print_timing` as a per-request latency.
Under continuous batching (`-np N`) it charges each slot the full shared
batch-step duration, inflating per-token times ~Nx. Trust the client-side
wall-clock, or measure single-stream on an idle server. (Mis-reading this once led
to a false "second bug" diagnosis.)

## Dispatch

`POST /admin/api/run` (login `admin`/`admin` first):
```json
{ "unit_ids": ["bc44bb0346"], "host_map": {"NVIDIA DGX Spark": "spark2-shanghai"} }
```
`host_map` resolves `device.class -> host_slug` when `device.host` is empty.
`device.class` must match a key in `HOST_FAMILIES` exactly. Restart uvicorn after
editing `main.py` (must run as `lkang`):
```bash
kill $(pgrep -f 'uvicorn main:app')
cd /home/amd/inferstation/admin_api && nohup /usr/bin/python3 -m uvicorn main:app \
  --host 127.0.0.1 --port 8201 --no-access-log >> /tmp/uvicorn-lkang.log 2>&1 & disown
```

## Known gaps / TODO

1. **Download not integrated** (`_build_serve_script` has `_ = spec` placeholder).
   Serve units assume the model is pre-staged under `/opt/inferstation/models`.
   Consequence: only spark2 (which has `Qwen3.6-35B-A3B-BF16.gguf`) can run today;
   halo6's model dir is empty → server won't start there. **This is step 2 of the
   flow and the reason the benchmark only ran on spark.** Fix: splice the offline
   download block into the serve script (ideally backgrounded so it overlaps
   container start, then `wait`).
2. **vLLM units unverified** — vLLM needs safetensors (not gguf), and the CPU-only
   vLLM container had a torch import issue. The 4 vLLM serve units have never run.
3. **Dispatcher not in git** — `main.py` / `ingest_runs.py` / `gen_serve_units.py`
   live only on the 4090. They should be vendored into this repo (e.g. under
   `bench/`) so changes are version-controlled and reviewable.
4. **`served-model-name` for vLLM** — `gen_serve_units.py` pins
   `--served-model-name <basename>` so the client's `--model` matches; verify when
   vLLM units first run.
